# ADR-0006: 顧客セルフサービス実行の提供方式

- ステータス: Proposed（未決定・実装保留）
- 日付: 2026-08-14
- 関連: [design-decisions.md](../design-decisions.md), [ADR-0003](0003-signed-url-delivery.md)

## コンテキスト

現在オンデマンド実行は `make run TENANT=…` のみで、これは **当社オペレーター用の CLI** である（tenants.json の読み取りと Workflow の起動権限を前提とする）。サブスクリプション型のサービスとして提供するなら、顧客が自分の意思で実行できる導線が要る、という整理を [design-decisions.md](../design-decisions.md) に記録済み。

CLI をそのまま顧客に渡すことはできない。理由:

- 実行には当社プロジェクトの Workflow 起動権限が必要で、テナント越しの権限分離ができない
- 全テナントの設定を含む `tenants.json` を読む
- 回数制限が無く、BigQuery スキャンと Gemini 呼び出しのコストが青天井

## 決定すべきこと

1. **導線の形**（ポータル UI / 認証付き API / 既存 SaaS への組み込み）
1. **認証方式**（誰がどう「そのテナントの人」だと証明するか）
1. **コスト制御**（実行回数の上限、課金するか否か）

## 選択肢

| 案                                                       | 長所                                               | 短所                                                     |
| :------------------------------------------------------- | :------------------------------------------------- | :------------------------------------------------------- |
| **認証付き HTTP API**（Cloud Run + IAP / Firebase Auth） | 実装が最小。既存 Workflow をそのまま再利用できる   | 顧客が API を叩く前提で、非エンジニアには使いにくい      |
| **Web ポータル**                                         | 顧客体験は最良。レポート履歴の閲覧も統合できる     | フロントエンド・認証・ホスティングが新規に必要で最も重い |
| **Slack スラッシュコマンド**                             | 既に Slack 連携するテナントには自然。UI 開発が不要 | Slack を使うテナント限定。Slack アプリの承認が要る       |
| **提供しない（現状維持）**                               | 追加コストゼロ。依頼ベースのコンサルに集中できる   | 顧客の「今すぐ見たい」に応えられない                     |

## 共通して必要になる仕組み（案によらず）

- **テナント境界の強制**: 認証主体からテナントを決定し、他テナントの `customer_project_id` を指定できないようにする（リクエストのパラメータを信用しない）
- **レート制限とコスト上限**: 1日あたりの実行回数上限。超過時は明確に拒否する
- **監査ログ**: 誰がいつどのテナントで実行したか
- **結果の返し方**: 既存どおり署名付きURL（[ADR-0003](0003-signed-url-delivery.md)）。恒常的な閲覧が要るならポータル側で都度発行する

## 保留の理由

事業判断（有償/無償、顧客体験の目標、開発工数の配分）が先に必要で、技術選定はその後に決まる。**現時点では `make run` は当社専用のままとし、顧客には定期レポートを提供する**という現行モデルを維持する。
